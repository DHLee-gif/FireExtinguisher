작업 순서는 사용자가 바꿨다: 스트리밍(6) → 불 감지(4) → 통합 시험(5). 스트리밍과 불 감지의 Pi 쪽 코드는 끝났다. 불 감지는 사진 수집과 학습이 오래 걸리기 때문이다.

## 지금 데이터가 어디까지 가나

선·LiDAR 패킷은 **Pi 안에서 STM32가 바로 읽을 수 있는 바이트 형태로 만들어진다.** 하지만 아직 UART로 나가지 않고
`/dev/shm/firecar/line.json`, `lidar.json`의 `packet` 필드(16진수 문자열)에만 들어 있다.
STM32 전송은 범위 밖으로 미뤄 두었다 (STM32는 다른 담당자, 연결 방식 미정).

STM32가 분기할 수 있게 모든 패킷에 다음이 있다:

| 상황 | LiDAR | 선 |
|---|---|---|
| 정상 | 회전 상태 `COMPLETE`, 구역별 `VALID` + 거리 mm | Status `0` 선 있음 + 치우침·각도·신뢰도 |
| 부분 정상 | `PARTIAL`, 받은 구역만 값, 안 본 구역은 mask로 표시 | 잠깐 놓쳐도 0.5초 동안 smooth 값 유지, `Lost` ms |
| 너무 가까움 | `TOO_CLOSE` (120mm 미만, 실제 거리도 보냄) + 요약 flag | - |
| 너무 멂·반사 없음 | `TOO_FAR`, `NO_RETURN` (검은 물체 의심 flag) | - |
| 선 없음 | - | Status `1` + 마지막으로 본 방향 |
| 센서·카메라 문제 | `NO_DATA`, `SENSOR_INVALID` | Status `2` 영상 없음, `3` 처리 오류 |
| 오래된 값 | 구역별 `age_ms` | `Age` ms |

값이 없으면 0이 아니라 `0xFFFF`/`0x7FFF`를 보낸다.

**나중에 `stm32/` 전송 프로그램을 만들 때 반드시 할 것** (자세한 건 각 패킷 문서):
- 새 `sequence`가 아니면 보내지 않는다 (Pi 프로세스가 죽으면 마지막 파일이 그대로 남아 있다).
- 기다린 시간을 패킷의 나이(Age)에 더하고 CRC를 다시 계산한다.
- STM32 쪽은 패킷이 일정 시간 안 오면 멈추는 watchdog을 둔다.
- 선 패킷과 LiDAR 주행 요약 패킷은 **초안**이다. STM32 담당자와 확정해야 한다.

## 단계별 상세

### 1. 카메라 (`camera/`)
- OV5647 카메라, 640×480, 30fps 설정 (실측 약 29fps).
- 카메라가 거꾸로 달려 있어서 `camera/config.toml`의 `rotate_180 = true`. 틀리면 선의 좌우가 반대로 나온다.
- 2초 동안 영상이 안 오면 프로세스가 종료하고 `main.py`가 다시 띄운다.

### 2. 선 인식 (`line/`)
- 흰색 선 1개를 화면 아래쪽 절반(`roi_top = 0.5`)에서 찾는다. 색은 `line/config.toml`의 `color` (white/black/yellow).
- 출력: 치우침(-1 왼쪽 ~ +1 오른쪽), 각도, 신뢰도, 후보 수, smooth 값, 변화 속도, 마지막 방향.
- 합성 영상으로 테스트 30개 통과. 실제 카메라에서 선이 없을 때 오류가 아니라 정확히 "선 없음(1)"이 나오는 것까지 확인.
- **안 된 것: 실제 바닥의 흰 선으로 확인.** 다른 담당자가 한다. 조명·바닥 반사에 따라 `line/config.toml`의 HSV 범위와
  `contrast`, `min_confidence`를 조정해야 할 수 있다. `line/preview.py`로 마스크를 그려 보면 쉽다 ([testing.md](testing.md)).
- 참고: 선 프로세스가 CPU 1코어를 거의 100% 쓴다 (Pi 4는 4코어라 지금은 문제없음). 불 감지를 붙일 때 CPU가 모자라면
  `line/config.toml`의 `scale`을 낮추는 것을 먼저 검토한다.

### 3. LiDAR (`lidar/run.py`)
- LiDAR TX → Pi GPIO15(핀 10, UART RX), 115200bps. `/dev/serial0` (= ttyS0). 연결 방법은 [setup.md](setup.md).
- 실측 (2026-11-26): 15초 동안 72회전 모두 `COMPLETE`, 5.2Hz, 회전당 정상 프레임 50·불량 0.
- 정면 방향: 물병으로 실측해 `lidar/config.toml`의 `forward_angle_deg = 10` (센서 케이블 반대쪽이 전방).
- 좌우 방향: 오른쪽에 물건을 두고 오른쪽 값으로 나오는 것 확인 (왼쪽은 같은 부호라 자동으로 맞음).
- **남은 것**
  - 줄자로 잰 실제 거리와 비교 (정확도 미확인).
  - LiDAR TX 전압(3.3V/5V) 미확인. Pi GPIO는 3.3V라 5V면 레벨 변환이 필요하다.
  - 예전 측정에서 -159° 방향 120mm 근처 점이 계속 보였다. 차체나 케이블일 수 있으니 실차에서 확인.
  - `lidar/config.toml`의 차 폭(`car_width_mm = 200`) 등은 임시값이다. 실측해서 바꾼다.
- 센서 없이 시험: 저장해 둔 데이터 `lidar/captures/COM5_2026-11-16.hex`로 재생 ([setup.md](setup.md)).

### 6. Wi-Fi 스트리밍 (`stream/`)
- 목적: **카메라 화면을 웹앱(사용자 화면)에서 실시간으로 본다.** 선·LiDAR 정보를 화면에 함께 보일지는 나중에 정한다.
- 방식: Pi가 웹앱 서버로 WebSocket 연결을 열고 JPEG 사진을 계속 보낸다 (초당 15장이면 눈에는 영상).
  규격은 [stream.md](stream.md).
- 웹앱 주소가 아직 없어 시험용 가상 웹앱(`stream/dev_server.py`)으로 확인했다. 실제 주소가 생기면
  `stream/config.toml`의 `server_url` 한 줄만 바꾼다.
- 실측 (2026-11-26): 실제 카메라로 15.2fps, 장당 약 20KB (약 300KB/s). 스트림 프로세스 CPU 약 17%.
- 고장 시험: 웹앱 서버를 끄자 스트림은 1·2·4초 간격으로 다시 연결을 시도했고 그동안 선·LiDAR 값은 계속 나왔다.
  서버를 다시 켜자 자동으로 다시 연결되어 화면이 나왔다.
- **남은 것**: 전원 켜면 자동 실행 서비스 설치 (sudo 필요, [setup.md](setup.md)). 실제 웹앱과 연결.

### 4. 불 감지 (`fire/`)
- Pi는 추론만 한다. PC에서 YOLO(`yolov8n`, 320px)를 학습해 ONNX로 바꿔 `fire/models/fire.onnx`에 넣는다.
- 완료: `fire/run.py`(추론, 최근 5장 중 3장 이상이면 `FIRE` 확정), 불 패킷 v1 22바이트(`C3 6C`), 사진 수집 `collect.py`,
  결과 그림 `preview.py`, 테스트 16개.
- 실제 Pi 확인 (2026-11-26): 모델이 없으면 죽지 않고 `NO_MODEL`("불 값 없음")을 보냄. 가짜 모델(항상 불)로
  카메라 → 추론 → 연속 판정(3장째 `FIRE`) → 패킷 경로 확인, 초당 5장, 선·LiDAR 영향 없음.
- 실제 불을 붙여 찍을 수 없어 공개 데이터셋 D-Fire(CC0)를 쓴다. 불만 남긴 5,100장을 `~/fire-train/dfire`에 준비했다.
- Pi에서 학습해 보니 1 epoch에 약 2시간이고 선 인식을 느리게 만들어서 중단했다.
- **지금은 공개 학습 모델 `rabahdev/fire-smoke-yolov8n`(D-Fire로 학습한 YOLOv8n)을 안전하게 변환해 쓴다.**
  시험 사진 600장에서 불 사진 88% 감지, 불 없는 사진 오탐 0%, 1장 약 300ms. 서비스에서 2Hz 유지, 선·LiDAR 영향 없음.
- **남은 것** (자세한 건 [fire.md](fire.md)):
  1. 휴대폰·모니터에 불꽃 사진·영상을 띄워 카메라 앞에서 `FIRE`가 되는지, 전등·햇빛에서 오탐이 없는지 확인
  2. (선택) Colab으로 직접 학습: `~/fire-train/dfire_fire.zip` + `fire/train/colab_train.ipynb`
  3. 불 패킷 규격을 STM32 담당자와 확정

## 결정 사항 기록

- 2026-11-26 Pi는 데이터 추출·가공(패킷 바이트 생성)까지. STM32 전송은 나중에 `stm32/`로 붙인다.
- 2026-11-26 실제 흰 선 확인은 다른 담당자가 맡는다.
- 2026-11-26 스트리밍 먼저, 불 감지는 그다음.
- 2026-11-26 스트리밍은 Pi가 웹앱 서버로 보낸다(push). 화면만 보내고 정보 표시는 나중에.
- 2026-11-26 `~/mjpg-streamer`는 쓰지 않는다.
- 2026-11-26 처리 주기는 LiDAR 한 바퀴(192ms) 기준: 선 15Hz, 불 2Hz, 스트림 10fps. 프로세스별 CPU 코어 분리.
- 2026-11-26 불 감지 모델은 Pi에서 학습하지 않는다. 지금은 공개 모델(rabahdev/fire-smoke-yolov8n), 입력 320, 기준 0.25.
- "프로세스 분리"는 기능마다 별도 프로세스(멀티프로세스)를 뜻한다.
