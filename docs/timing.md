# 처리 주기와 CPU 배분

원칙: **프로세스끼리 영향을 주지 않는다.** 그래서 각 프로세스는 "할 수 있는 만큼 빨리"가 아니라 정한 주기로만 돌고,
CPU 코어도 나눠 쓴다. 우선순위는 선 인식·LiDAR > 불 감지 > 스트리밍.

## 기준: LiDAR 한 바퀴

LiDAR는 센서가 정한 속도로 돈다. 실측 **5.2회/초 = 한 바퀴 약 192ms**. 이게 장애물 정보가 새로 오는 가장 빠른 주기다.

- 장애물 값의 나이: 최악의 경우 한 바퀴(192ms) + 입력 버퍼 여유(100ms) ≈ **0.3초** (패킷의 `age_ms`).
- STM32는 이 0.3초 동안(통신·제동 시간은 별도) 차가 장애물을 못 보고 달린다고 봐야 한다.

### 그래서 차 속도의 상한

못 보고 달려도 되는 거리를 `D`라 하면 `최고 속도 ≈ D ÷ 0.3초` (여기에 제동거리와 STM32 처리 시간은 따로 더 남겨야 한다).

| 못 보고 달려도 되는 거리 D | 최고 속도 |
|---:|---:|
| 10 cm | 약 0.33 m/s |
| 20 cm | 약 0.66 m/s |
| 30 cm | 약 1.0 m/s |

`D`는 실차에서 정한다 (STM32 담당자와). 아래 주기는 **0.33 m/s 정도**를 가정해 골랐다.

## 프로세스별 주기

| 프로세스 | 주기 | 근거 | 설정 |
|---|---|---|---|
| LiDAR | 회전마다 (5.2Hz) | 센서가 정함 | - |
| 카메라 촬영 | 30fps | 영상이 늘 새것(33ms 이내)이 되게. 읽는 쪽이 최신 1장만 가져간다 | `camera/config.toml` `fps` |
| 선 인식 | **15Hz** (LiDAR 한 바퀴에 약 3번) | 0.33 m/s에서 처리 한 번에 약 2cm 이동. 선 폭(약 2cm)과 같은 수준이라 조향에 충분 | `line/config.toml` `max_fps` |
| 불 감지 | **2Hz** | 불은 움직이지 않는다. 최근 5장 중 3장 → 확정까지 약 1~2.5초. 그동안 차는 약 0.3~0.8m 이동하는데, 불은 2~3m 앞에서 보이므로 충분 | `fire/config.toml` `max_fps` |
| 스트리밍 | **10fps** | 사람이 화면을 보는 용도 | `stream/config.toml` `fps` |

선 인식의 `smoothing`은 처리 1번마다 적용되므로 주기를 바꾸면 같이 바꾼다 (30fps에서 0.5 → 15fps에서 0.75면 같은 반응 속도).

### 나중에 STM32로 보낼 주기 (`stm32/` 만들 때)

새 값이 나올 때마다 보내면 된다. 같은 Sequence는 다시 보내지 않는다.

| 패킷 | 크기 | 주기 | 바이트/초 |
|---|---:|---:|---:|
| LiDAR v3 + 주행 요약 | 69 + 21 | 5.2Hz | 약 470 |
| 선 v2 | 25 | 15Hz | 약 375 |
| 불 v1 | 22 | 2Hz | 약 44 |
| 합계 | | | **약 890** |

UART 115200bps는 약 11,500바이트/초라서 **약 8%**만 쓴다. 여유가 충분하다.

## CPU 코어 배분 (`main.toml`)

Raspberry Pi 4는 코어가 4개다. `main.py`가 프로세스마다 쓸 코어를 정해 띄운다.

| 코어 | 프로세스 | 이유 |
|---|---|---|
| 0 | camera, lidar | 둘 다 가볍다 (각 약 20%) |
| 1 | line | 선 인식만 혼자 쓴다. 다른 것이 아무리 바빠도 선 인식 코어를 뺏지 못한다 |
| 2 | fire (`nice 5`), stream (`nice 10`) | 우선순위 낮은 둘. 둘이 이 코어 안에서만 나눠 쓴다. 불 감지가 이 코어의 약 60%를 써서, 바쁠 때는 우선순위가 가장 낮은 스트림이 장수를 덜 보낸다 |
| 3 | 비워 둠 | OS, 화면, 원격 접속 등 |

선 인식은 OpenCV 스레드를 1개만 쓴다 (`cv2.setNumThreads(1)`). 불 감지도 1개 (`fire/config.toml` `threads`).

## 실측 (2026-11-26, Raspberry Pi 4)

| 항목 | 주기 조정 전 | 조정 후 |
|---|---|---|
| 선 인식 | 약 29Hz, CPU 100%+ (학습을 같이 돌리자 18~21Hz로 떨어짐) | 14.7Hz, CPU 약 45% (한 코어 기준) |
| 선 인식이 쓰는 영상의 나이 | - | 중간값 47ms, 최대 77ms |
| LiDAR | 5.2Hz | 5.2Hz |
| 불 감지 | 5Hz 설정 | 2.0Hz. 모델 1장 약 300ms → 코어 2의 약 60% |

조정 후 무거운 작업(모델 학습)을 같이 돌렸을 때도 선 14.4Hz, LiDAR 5.3Hz, 불 2.0Hz를 유지했다
(그때 영상 나이 중간값 60ms, 최대 131ms).

## 지킬 것

- 주기를 올리기 전에 이 표의 근거부터 다시 본다. 선 인식 코어(1)에 다른 프로세스를 넣지 않는다.
- 모델 학습 같은 무거운 작업은 차량 서비스가 도는 Pi에서 하지 않는다 ([fire.md](fire.md)).
  꼭 Pi에서 해야 하면 `sudo systemctl stop firecar`로 서비스를 멈추고 한다.
